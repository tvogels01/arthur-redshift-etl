etl.design.load module

etl.design.load module¶

Slurp in “table design” files and validate the relation’s design.

Table designs describe the columns, like their name and type, as well as how the data should be organized once loaded into Redshift, like the distribution style or sort key.

Table designs are implemented as dictionaries of dictionaries or lists etc.

etl.design.load.load_table_design(stream, table_name)[source]¶

Load table design from stream (usually, an open file).

The table design is validated before being returned.

etl.design.load.load_table_design_from_localfile(local_filename, table_name)[source]¶

Load (and validate) table design file in local file system.

etl.design.load.load_table_design_from_s3(bucket_name, design_file, table_name)[source]¶

Download (and validate) table design from file in S3.

etl.design.load.validate_column_references(table_design)[source]¶

Make sure that table attributes and constraints only reference columns that actually exist.

etl.design.load.validate_identity_as_surrogate_key(table_design)[source]¶

Check whether specification of our identity column is valid and matches surrogate key.

etl.design.load.validate_semantics_of_ctas(table_design)[source]¶

Check for semantics that apply only to CTAS.

etl.design.load.validate_semantics_of_table(table_design)[source]¶

Check for semantics that apply to tables in source schemas.

etl.design.load.validate_semantics_of_table_or_ctas(table_design)[source]¶

Check for semantics that apply to tables that are in source schemas or are a CTAS.

etl.design.load.validate_semantics_of_view(table_design)[source]¶

Check for semantics that only apply to views.

Basically, definitions of views may only contain column names or descriptions. Note that validation doesn’t catch this since we didn’t completely separate the schema for CTAS and VIEW but have that distinction only on the source_name.

etl.design.load.validate_table_design(table_design, table_name)[source]¶

Validate table design against schema. Raise exception if anything is not right.

Phase 1 of validation is based on a schema and json-schema validation. Phase 2 is built on specific rules that I couldn’t figure out how to run inside json-schema.

etl.design.load.validate_table_design_semantics(table_design, table_name)[source]¶

Validate table design against rule set based on values (e.g. name of columns).

Raise an exception if anything is amiss.

etl.design.load.validate_table_design_syntax(table_design, table_name)[source]¶

Validate table design based on the (JSON) schema (which can only check syntax but not values).

Raise an exception if anything is amiss.
